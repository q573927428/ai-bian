## 交易系统扩容评估与优化方案（8×4 → 20×10）

### 1. 背景与目标

当前系统规模：
- 交易对：8
- 策略：4

目标评估规模：
- 交易对：20
- 策略：10

本方案目标：
1. 评估现有架构在 20×10 下的压力风险。
2. 明确当前瓶颈是否会导致明显性能问题。
3. 给出分阶段、可落地的优化改造路径。

---

### 2. 现状执行链路（基于代码）

核心链路：
1. `server/plugins/strategy-manager.ts` 启动策略系统。
2. `server/modules/strategy-manager/index.ts` 初始化 `StrategyEngine`、`IndicatorsHub`、`PositionManager`。
3. `StrategyEngine` 为每个激活策略启动独立定时循环。
4. 每轮策略循环按该策略 symbols 串行分析：
   - 仓位冲突检查
   - 指标获取（`IndicatorsHub`）
   - 拉取最新价格（`fetchPrice`）
   - AI 评估（`MultiStrategyAIAnalyzer`）
   - 信号验证与交易执行

指标层现状：
- `IndicatorsHub` 已具备统一 K 线缓存、OI 去重、文件 mtime 增量检查。
- 周期刷新中会清空 symbol 维度指标缓存，导致后续分析重算。

数据同步现状：
- `server/plugins/kline-sync.ts` 按配置周期进行多交易对 K 线同步。
- symbols 来自 `data/bot-config.json`。

---

### 3. 20×10 场景压力结论

结论：**服务器压力会明显增加**，但主要不在“基础指标数学计算”，而在“任务模型 + AI调用 + I/O模式 + 外部API访问密度”。

#### 3.1 复杂度放大
- 现有主模型是“每策略定时器 + 每策略遍历交易对”。
- 扩容后单轮理论分析任务量接近 `策略数 × 每策略交易对数 = 10 × 20 = 200`。
- 若策略之间交易对高度重叠，会产生大量重复分析路径。

#### 3.2 主要瓶颈

1) **AI 调用瓶颈（首要）**
- 缓存存在但在行情波动时命中率有限。
- 扩容后 AI 请求峰值、等待时间、失败重试概率都会上升。

2) **外部 API 访问压力**
- 每个分析任务通常要取 price，OI 也存在周期刷新。
- 容易触发限流或响应抖动，影响策略延迟。

3) **文件 I/O 放大**
- AI 分析写盘当前是“读全量 JSON -> 追加 -> 全量写回”。
- 高并发时会明显放大磁盘开销和事件循环阻塞风险。

4) **事件循环抖动**
- 多策略定时器叠加触发时，会形成峰值并发（扫描高峰对齐）。

#### 3.3 稳定性判断
- 在 20×10 下并非必然崩溃，但在高波动、扫描周期较短、策略覆盖重叠时，
  会出现：
  - 扫描延迟增大
  - AI 超时/失败率升高
  - 漏信号概率提升
  - 交易决策“过期执行”风险上升

---

### 4. 架构优化空间（优先级）

## P0（优先立即实施）

### 4.1 调度模型重构：从“按策略循环”改为“按交易对聚合调度”

现状问题：
- 同一 symbol 被不同策略重复触发拉数与计算。

改造建议：
- 先按 symbol 构建一次市场快照（price + K线引用 + 指标快照）。
- 再将该快照扇出给订阅该 symbol 的策略。

收益：
- 重复计算减少。
- API 请求可复用。
- 任务模型更易做统一限流。

涉及模块：
- `server/modules/strategy-engine/StrategyEngine.ts`
- `server/modules/strategy-manager/StrategyManager.ts`

### 4.2 引入全局并发闸门（关键）

建议增加三类并发池：
1. 指标计算并发池
2. AI 请求并发池
3. 交易 API 并发池

建议初始值（可配置）：
- indicatorConcurrency: 8~16
- aiConcurrency: 3~6
- tradeApiConcurrency: 2~4

收益：
- 防止高峰期“瞬时洪峰”导致雪崩。

### 4.3 AI 预筛短路机制

在调用 AI 前做轻量规则筛选（本地计算）：
- 趋势强度不足（ADX 低）
- 波动不足（ATR 低）
- 成交量异常不足

未通过预筛的任务直接 `IDLE`，不调用 AI。

收益：
- AI 请求量显著下降（通常可下降 30%~70%，取决于策略条件）。

---

## P1（高收益优化）

### 4.4 指标缓存失效策略精细化

现状：
- 刷新逻辑中存在 symbol 维度清空指标缓存。

建议：
- 改成“symbol + timeframe + indicatorType”粒度失效。
- 仅在对应 K 线更新后失效对应指标。

涉及模块：
- `server/modules/indicators/IndicatorsHub.ts`

### 4.5 统一价格/OI 快照复用

建议：
- 将 `fetchPrice(symbol)` 从策略内重复调用，改成调度轮次内一次获取，多策略复用。
- OI 继续统一集中更新，并给策略读取统一快照。

### 4.6 AI 分析落盘改造（减少重写）

现状：
- `MultiStrategyAIAnalyzer.saveAIAnalysisToFile` 读写整文件。

建议：
- 改为 JSONL append（按行写）或批量缓冲（例如 1~3 秒 flush 一次）。
- 按日分文件继续保留，避免单文件过大。

收益：
- 明显降低磁盘写放大和事件循环阻塞。

---

## P2（中长期）

### 4.7 任务队列分层

将分析流程拆分为：
1. 市场数据任务
2. 策略评估任务
3. AI 任务
4. 交易执行任务

每层有独立队列和并发配额，支持降级策略（例如 AI 过载时优先高权重策略）。

### 4.8 可观测性与容量基线

新增监控指标：
- 每轮扫描耗时 / P95
- AI 请求耗时 / P95 / 失败率
- 缓存命中率（指标缓存、AI缓存）
- API 错误码分布（限流、超时）
- 事件循环延迟

基于监控做动态调参（并发阈值、扫描间隔、预筛阈值）。

### 4.9 横向扩展预留

按 symbol 哈希分片，为多 worker / 多进程预留边界；
后续可做：
- 分片策略执行
- 分片缓存
- 分片 AI 调度

---

### 5. 建议实施顺序（两周版）

#### 第 1 周（稳态优先）
1. 增加全局并发闸门（AI/API/指标）
2. 加入 AI 预筛短路
3. 优化 AI 落盘为 append/batch
4. 增加关键监控日志与耗时统计

#### 第 2 周（结构优化）
1. 改造“按交易对聚合调度 + 策略扇出”
2. 指标缓存按粒度失效
3. 价格快照统一复用

---

### 6. 验收指标（建议）

优化完成后至少达成：
1. 单轮扫描总耗时下降 ≥ 40%
2. AI 请求总量下降 ≥ 35%
3. AI 超时率下降 ≥ 50%
4. 事件循环延迟峰值下降 ≥ 30%
5. 在 20×10 下连续运行 24h 无明显积压/雪崩

---

### 7. 风险与回滚

风险点：
1. 调度模型重构可能影响当前信号触发时序。
2. 预筛阈值过严可能导致信号变少。
3. 并发阈值配置不当可能造成吞吐过低。

回滚策略：
1. 关键改造全部加 feature flag。
2. 新旧调度可切换（按配置开关）。
3. 预筛逻辑可按策略启停。

---

### 8. 最终结论

在当前代码结构下，从 8×4 扩到 20×10，系统会承压明显，核心风险在：
- 多策略重复调度
- AI 调用放大
- 文件 I/O 写放大

系统有较好的基础（统一指标中心已在位），具备较强优化空间。建议按本方案分阶段执行，先控峰值、再改调度，可在不大改业务语义的前提下获得显著性能提升与稳定性提升。
