# 短期效率优化修改方案

本文档针对当前项目在“策略增多、交易对增多、未来多用户商用”场景下的短期可落地优化进行拆解。目标不是一次性重构成完整 SaaS 架构，而是在现有 Nuxt/Nitro 单体结构内，优先降低 AI API、Binance API、指标计算和策略循环的重复消耗，并为后续多用户隔离打基础。

## 1. 当前核心链路

当前启动链路：

```text
server/plugins/kline-sync.ts
  -> KLineSimpleSyncService
  -> sql.js K线数据库

server/plugins/position-manager.ts
  -> PositionManager 单例
  -> data/active-positions.json
  -> data/symbol-locks.json

server/plugins/strategy-manager.ts
  -> initStrategyManager()
  -> StrategyStore
  -> BinanceService
  -> IndicatorsHub
  -> StrategyEngine
  -> SymbolBasedScheduler
  -> MultiStrategyAIAnalyzer
```

当前策略扫描链路：

```text
StrategyEngine.globalStrategyLoop()
  -> 按到期策略收集 symbol
  -> SymbolBasedScheduler.buildMarketSnapshot(symbol)
  -> IndicatorsHub.getBatchIndicators()
  -> StrategyEngine.analyzeSymbol(strategy, symbol, snapshot)
  -> StrategyEngine.callAI()
  -> MultiStrategyAIAnalyzer.analyze()
  -> callAIAPI()
  -> executeSignal()
  -> BinanceService 下单
```

当前已有优化：

- `SymbolBasedScheduler` 已经按交易对聚合市场快照。
- `IndicatorsHub` 已经集中缓存 K 线和指标。
- `concurrencyPoolManager` 已经控制指标、AI、交易 API 并发。
- `binanceApiGateway` 已经集中做 Binance 请求限流。
- `aiRateLimit` 已经有每分钟、每轮扫描、超时和错误冷却配置。

当前主要短板：

- `globalStrategyLoop()` 没有运行中锁，长扫描可能重入。
- AI 缓存键包含 `strategyId`，不同策略无法共享相同输入的 AI 结果。
- `SymbolBasedScheduler` 构建快照时只聚合默认指标类型，策略参数化指标仍在 `analyzeSymbol()` 内逐策略二次计算。
- `PositionManager` 使用 `symbol` 作为全局锁键，未来多用户或多账户会互相影响。
- 当前 `bot-config.json` 只能配置并发数，缺少更细的运行保护和观测指标。

## 2. 短期优化目标

### 2.1 性能目标

在不大改项目架构的前提下，将扫描成本从：

```text
策略数 * 交易对数 * 指标计算/AI调用
```

逐步压低到：

```text
交易对数 * 参数组合数 + 候选信号数 * AI调用
```

### 2.2 安全目标

- 防止策略扫描循环重入。
- 防止一轮扫描耗时过长时重复触发下一轮。
- 保证 Binance 交易 API 优先级仍高于行情和账户查询。
- 保留现有风控逻辑，不因为优化而放宽交易条件。

### 2.3 可扩展目标

- 为 `userId/accountId` 维度预留字段和锁键格式。
- 为后续队列化 Worker 和数据库迁移减少耦合。
- 不改变前端使用方式，不影响现有策略配置。

## 3. 核心修订：指标组合统一预计算

### 3.1 结论

“所有指标组合每 5 分钟统一计算一次，然后不同策略只提取已经计算好的数据”是当前项目最应该优先做的短期优化之一。

但需要准确理解它的边界：

- 对“指标计算”来说，这个方案可以基本摆脱策略数量线性增长。
- 对“AI 调用”来说，还需要配合 AI 缓存、预筛和批处理，否则策略多时仍会消耗大量 AI API。
- 对“Binance 私有 API”来说，多用户仍然需要账户级隔离，不能只靠指标预计算解决。
- 对“行情数据”来说，应继续保持全局共享，同一交易对同一周期只同步一次 K 线。

也就是说，指标层可以做到：

```text
交易对数 * 周期数 * 实际参数组合数
```

而不是：

```text
交易对数 * 策略数 * 指标数
```

如果 200 个策略大多使用相同 RSI(14)、ADX(14)、ATR(14)、MACD(12,26,9)、相近 EMA 组合，那么指标计算压力会大幅下降。

### 3.2 不能按“理论所有组合”计算

`app/components/StrategyEditor.vue` 当前暴露的指标配置大致是：

- EMA：从 `7/14/20/30/50/60/120/200` 中选择 2 到 3 个。
- RSI：固定 `period=14`。
- ADX：固定 `period=14`。
- MACD：固定 `12/26/9`。
- ATR：固定 `period=14`。
- Volume：固定 `comparePeriod=20`。
- OI：`changePeriod` 和 `trendThresholdPercent` 可调。
- SquareHeat：按 symbol 维度获取。

EMA 理论组合数量已经不少，OI 参数理论组合更多。因此不要启动时把所有理论组合都算完。正确方式是：

```text
只统计当前启用策略真正用到的指标组合
只对这些组合预计算
策略修改/启停/交易对热重载时刷新组合注册表
```

### 3.2.1 推荐进一步收敛组合空间

根据当前讨论，建议直接把策略编辑器的组合空间收敛为固定商用配置：

- EMA 可选周期从 8 个减少到 5 个。
- 每个策略仍选择 2 到 3 个 EMA。
- K 线周期固定为 `5m/15m/1h/4h/1d`。
- RSI 固定 `14`。
- ADX 固定 `14`。
- ATR 固定 `14`。
- MACD 固定 `12/26/9`。
- Volume 固定 `comparePeriod=20`。
- OI 固定 `changePeriod=8`、`trendThresholdPercent=0.003`。
- SquareHeat 不按 K 线周期计算，只按交易对缓存。

这样做的收益非常直接：指标组合空间从“策略自定义无限扩散”变成“可控的固定组合池”。

如果 EMA 只有 5 个可选周期，并且每个策略选 2 到 3 个：

```text
EMA 组合数 = C(5,2) + C(5,3)
= 10 + 10
= 20 种
```

每个交易对每个周期的组合：

```text
EMA 20
+ RSI 1
+ ADX 1
+ MACD 1
+ ATR 1
+ Volume 1
+ OI 1
= 26 种
```

5 个周期：

```text
26 * 5 = 130 种
```

SquareHeat 不依赖周期：

```text
每个交易对总组合 = 130 + 1 = 131 种
```

100 个交易对理论最大缓存项：

```text
100 * 131 = 13,100 个组合
```

这已经是非常可控的规模。实际运行时，如果只计算活跃策略真实使用的 EMA 组合，还会比 13,100 更少。

### 3.2.2 不同数据类型应使用不同刷新频率

虽然可以统一注册组合，但不建议所有数据都每 5 分钟调用外部接口。

建议刷新频率：

| 数据类型 | 计算/刷新方式 | 推荐频率 |
| --- | --- | --- |
| EMA/RSI/ADX/MACD/ATR/Volume | 本地 K 线计算 | 每 5 分钟 |
| OI 当前值 | Binance API 或缓存 | 5-10 分钟 |
| OI History | Binance API，按周期分级缓存 | 5m/15m: 5-10 分钟；1h: 15-30 分钟；4h/1d: 30-60 分钟 |
| SquareHeat | 外部热度数据 | 15-30 分钟 |
| K 线 | 同步服务更新 | 按周期同步，短周期优先 |

原因：

- 技术指标是本地计算，CPU 压力可控。
- OI history 和 SquareHeat 涉及外部 API，才是真正的限频风险。
- 4h/1d 这类慢周期没必要每 5 分钟刷新外部统计数据。

### 3.2.3 对 StrategyEditor 的调整建议

建议同步修改 `app/components/StrategyEditor.vue`：

1. EMA 可选周期减少为 5 个，例如：

```text
14 / 20 / 50 / 60 / 120
```

或按你的策略体系固定另一组 5 个。

2. OI 参数不再开放输入，固定为：

```ts
changePeriod: 8
trendThresholdPercent: 0.003
```

3. 如果仍需要展示 OI 参数，可以改成只读说明，不提供编辑控件。

4. 保存策略时强制归一化，防止旧策略或接口绕过前端写入其他参数。

服务端也要做归一化，不能只依赖前端：

```text
StrategyStore.createStrategy()
StrategyStore.updateStrategy()
StrategyStore.updateStrategyWithoutVersion()
```

保存前统一调用 `normalizeStrategyIndicatorConfig(strategy)`，把 OI、RSI、ADX、ATR、MACD、Volume 参数收敛到固定值。

### 3.3 新增指标组合注册表

建议新增模块：

```text
server/modules/indicator-registry/IndicatorCombinationRegistry.ts
```

职责：

1. 扫描所有运行中策略。
2. 提取每个策略实际需要的指标组合。
3. 按 `symbol + timeframe + indicatorType + paramsHash` 去重。
4. 维护组合到策略的反向映射。
5. 给预计算服务提供组合列表。

建议核心类型：

```ts
export interface IndicatorCombination {
  key: string
  symbol: string
  timeframe: Timeframe
  type: IndicatorType | StatisticsType
  params: Record<string, any>
}

export interface StrategyIndicatorBinding {
  strategyId: StrategyId
  symbol: string
  mainTimeframe: Timeframe
  keys: {
    ema?: string
    rsi?: string
    adx?: string
    macd?: string
    atr?: string
    oi?: string
    volume?: string
    squareHeat?: string
  }
}
```

组合 key 示例：

```text
BTC/USDT:1h:EMA:periods_14_60_120
BTC/USDT:1h:RSI:period_14
BTC/USDT:1h:ADX:period_14
BTC/USDT:1h:MACD:fast_12_slow_26_signal_9
BTC/USDT:1h:ATR:period_14
BTC/USDT:1h:OI:change_12_threshold_0.05
BTC/USDT:1h:Volume:compare_20
BTC/USDT:1h:SquareHeat:default
```

### 3.4 新增指标预计算服务

建议新增模块：

```text
server/modules/indicator-precompute/IndicatorPrecomputeService.ts
```

职责：

1. 每 5 分钟读取 `IndicatorCombinationRegistry` 的组合列表。
2. 对每个组合调用 `IndicatorsHub` 计算指标。
3. 将结果写入内存缓存。
4. 策略扫描时只读缓存，不再逐策略临时计算。
5. K 线同步事件触发时，可标记相关组合 dirty，下一轮优先刷新。

建议核心缓存：

```ts
private cache = new Map<string, {
  data: IndicatorData
  computedAt: number
  sourceKlineTimestamp?: number
}>()
```

建议对外接口：

```ts
get(key: string): IndicatorData | undefined
getMany(keys: string[]): Map<string, IndicatorData>
precomputeAll(): Promise<void>
markDirtyBySymbolTimeframe(symbol: string, timeframe: Timeframe): void
```

### 3.5 预计算周期

默认每 5 分钟计算一次是合理的，因为当前 `StrategyEngine` 最小扫描间隔也是 5 分钟。

建议新增配置：

```json
{
  "indicatorPrecompute": {
    "enabled": true,
    "intervalMs": 300000,
    "maxConcurrency": 8,
    "staleTtlMs": 900000,
    "computeOnStrategyChange": true,
    "technicalIndicatorIntervalMs": 300000,
    "oiFastIntervalMs": 600000,
    "oiSlowIntervalMs": 1800000,
    "squareHeatIntervalMs": 1800000
  }
}
```

含义：

- `intervalMs`: 默认 5 分钟统一刷新。
- `maxConcurrency`: 预计算并发，不要无限并发。
- `staleTtlMs`: 如果预计算失败，允许短时间使用旧指标。
- `computeOnStrategyChange`: 策略启停、保存后立即刷新新增组合。
- `technicalIndicatorIntervalMs`: EMA/RSI/ADX/MACD/ATR/Volume 的本地计算周期。
- `oiFastIntervalMs`: 5m/15m OI 刷新周期。
- `oiSlowIntervalMs`: 1h/4h/1d OI 刷新周期。
- `squareHeatIntervalMs`: SquareHeat 刷新周期。

### 3.6 StrategyEngine 使用方式

当前 `StrategyEngine.callAI()` 内会再次调用：

```ts
this.indicatorsHub.getIndicators(...)
this.indicatorsHub.getEMAByPeriods(...)
```

修改后改成：

```text
StrategyEngine.analyzeSymbol()
  -> 从 registry 获取该 strategyId + symbol 的 binding
  -> 从 IndicatorPrecomputeService 按 key 读取已算好的指标
  -> 组装 indicatorsData
  -> 预筛
  -> AI 缓存/AI 调用
```

短期保留兜底：

```ts
const cached = precomputeService.get(key)
if (cached) {
  indicatorsData.set(`${timeframe}_${type}`, cached)
} else {
  logger.warn('StrategyEngine', `预计算指标缺失，回退实时计算: ${key}`)
  // 使用旧逻辑实时计算，避免中断交易系统
}
```

等稳定后再把旧的实时计算路径降级为测试/修复工具。

### 3.7 和 SymbolBasedScheduler 的关系

预计算方案落地后，`SymbolBasedScheduler.buildMarketSnapshot()` 不再负责临时批量计算所有参数化指标，它只需要负责：

- 当前价格。
- K 线引用。
- 基础市场快照。
- 取出对应策略的预计算指标结果。

新的分工：

```text
KLineSimpleSyncService
  -> 负责同步 K 线

IndicatorsHub
  -> 负责单个指标的计算和底层缓存

IndicatorCombinationRegistry
  -> 负责知道哪些组合需要算

IndicatorPrecomputeService
  -> 负责每 5 分钟统一把组合算好

StrategyEngine
  -> 负责按策略提取结果、预筛、AI、交易执行
```

### 3.8 这样是否“不管多少策略都可以”

不能绝对说“不管多少策略都可以”，但可以说：

```text
只要策略共享的指标组合有限，指标计算基本不再怕策略数量增加。
```

举例：

100 个用户、200 个策略，如果大家都看同一批 30 个交易对，且指标组合集中在：

- EMA 10 种组合以内
- RSI 1 种
- ADX 1 种
- ATR 1 种
- MACD 1 种
- OI 5 到 10 种
- Volume 1 种

那么每 5 分钟要算的是：

```text
30 个交易对 * 有限指标组合
```

而不是：

```text
200 个策略 * 30 个交易对 * 多个指标
```

这会有数量级提升。

但是以下部分仍会随用户或策略增加：

- AI prompt 不同导致的 AI 调用。
- 用户账户余额、持仓、订单查询。
- 下单、撤单、止损单维护。
- 每个用户的风控、持仓监控、日志和交易历史。

因此该方案解决“指标计算不随策略线性爆炸”，但不等于完整解决“100 用户商用架构”。

### 3.9 落地优先级

建议把原第三阶段“指标参数聚合到快照”升级为：

```text
指标组合注册表 + 5分钟统一预计算 + 策略按 key 读取结果
```

这是比“扫描时聚合计算”更彻底、更适合多策略的方案。

## 4. 修改点一：给全局策略循环增加运行锁

### 3.1 问题

文件：

```text
server/modules/strategy-engine/StrategyEngine.ts
```

当前定时器启动位置：

```ts
this.globalTimer = setInterval(() => {
  void this.globalStrategyLoop()
}, this.globalScanInterval)
```

如果一轮扫描因为 AI API 慢、Binance 限流、交易对过多而超过 `globalScanInterval`，下一轮仍会进入 `globalStrategyLoop()`。这会导致：

- 同一批策略重复扫描。
- `currentLoopAIRequests` 互相覆盖。
- 并发池队列堆积。
- Binance 和 AI 请求变成雪崩式排队。

### 3.2 设计

在 `StrategyEngine` 增加两个状态字段：

```ts
private isGlobalLoopRunning = false
private skippedLoopCount = 0
```

在 `globalStrategyLoop()` 开头加锁：

```ts
private async globalStrategyLoop(): Promise<void> {
  if (this.isGlobalLoopRunning) {
    this.skippedLoopCount++
    logger.warn('StrategyEngine', `上一轮扫描尚未完成，跳过本次扫描，累计跳过 ${this.skippedLoopCount} 次`)
    return
  }

  this.isGlobalLoopRunning = true
  const loopStartTime = Date.now()

  try {
    // 原有逻辑
  } catch (error: any) {
    logger.error('StrategyEngine', `全局策略循环异常: ${error.message}`)
  } finally {
    this.isGlobalLoopRunning = false
  }
}
```

### 3.3 额外建议

增加一条耗时日志：

```ts
const duration = Date.now() - loopStartTime
logger.info('StrategyEngine', `本轮扫描结束，耗时 ${duration}ms，跳过计数 ${this.skippedLoopCount}`)
```

如果 `duration > globalScanInterval * 0.8`，输出 warn，提示需要调大批次延迟、减少交易对或降低 AI 调用量。

### 3.4 验证方式

1. 临时把 `strategyScheduler.symbolBatchDelayMs` 调大。
2. 启动多个策略。
3. 观察日志是否出现“上一轮扫描尚未完成，跳过本次扫描”。
4. 确认没有并发进入同一轮扫描。

### 3.5 风险

风险较低。跳过扫描比重入更安全，因为交易系统宁可少扫一轮，也不能重复触发交易判断。

## 5. 修改点二：优化 AI 缓存键，减少重复 AI 调用

### 4.1 问题

涉及文件：

```text
server/modules/strategy-engine/StrategyEngine.ts
server/modules/ai-analyzer/MultiStrategyAIAnalyzer.ts
```

当前存在两层 AI 缓存：

```text
StrategyEngine.aiCache
MultiStrategyAIAnalyzer 模块级 aiCache
```

两个缓存键都包含 `strategyId`。结果是：

- 策略 A 和策略 B 只要 ID 不同，就不会共享缓存。
- 即使两者 prompt、指标、价格、K 线完全一致，也会重复调用 AI。
- 策略越多，AI API 成本几乎线性增长。

### 4.2 短期设计原则

不能简单删除 `strategyId`，因为不同策略的 `userPrompt` 可能不同。正确做法是把缓存维度从：

```text
strategyId + symbol + indicatorsHash
```

调整为：

```text
symbol + marketDataHash + promptHash + rulesHash + providerHash + modelHash
```

也就是：相同市场数据、相同提示词、相同规则、相同模型，才共享缓存。

### 4.3 建议新增工具函数

新增文件：

```text
server/utils/stable-hash.ts
```

用途：生成稳定 hash，避免 `JSON.stringify()` 对 Map/Object 顺序敏感。

建议接口：

```ts
export function stableStringify(value: unknown): string
export function shortHash(value: unknown, length = 32): string
```

实现建议：

- `Map` 转成按 key 排序的数组。
- 普通对象按 key 排序。
- 数字保留有限精度，避免价格极小变化导致缓存全部失效。
- 使用 `Buffer.from(stableStringify(value)).toString('base64').substring(0, length)` 即可短期使用。

### 4.4 修改 StrategyEngine 缓存键

当前方法：

```ts
private buildAICacheKey(
  strategyId: StrategyId,
  symbol: string,
  indicatorsData: Map<string, any>
): string
```

建议改为：

```ts
private buildAICacheKey(
  symbol: string,
  indicatorsData: Map<string, any>,
  promptConfig: AIPromptConfig,
  structuredRules?: unknown
): string
```

缓存键内容：

```ts
const cachePayload = {
  symbol,
  indicatorsData,
  userPrompt: promptConfig.userPrompt,
  provider: promptConfig.provider,
  model: promptConfig.model,
  temperature: promptConfig.temperature,
  structuredRules
}
return `ai:${symbol}:${shortHash(cachePayload)}`
```

调用处从：

```ts
const cacheKey = this.buildAICacheKey(strategyId, symbol, indicatorsData)
```

改成：

```ts
const cacheKey = this.buildAICacheKey(
  symbol,
  indicatorsData,
  promptConfig,
  (instance.strategy as any).structuredRules
)
```

### 4.5 修改 MultiStrategyAIAnalyzer 缓存键

当前方法：

```ts
private buildCacheKey(
  strategyId: StrategyId,
  symbol: string,
  indicators: TechnicalIndicators,
  price: number,
  volume: number = 0,
  candleProgress: number = 0.1,
  promptConfig?: AIPromptConfig
): string
```

建议保留参数但不要把 `strategyId` 放入最终 key。改成：

```ts
const hash = shortHash({
  symbol,
  indicators,
  price: Number(price.toFixed(2)),
  volume: Number(volume.toFixed(2)),
  candleProgress: Number(candleProgress.toFixed(4)),
  userPrompt: promptConfig?.userPrompt,
  provider: promptConfig?.provider,
  model: promptConfig?.model,
  temperature: promptConfig?.temperature
})

return `ai:${symbol}:${hash}`
```

### 4.6 需要保留的安全边界

以下字段必须进入缓存键：

- `promptConfig.userPrompt`
- `promptConfig.provider`
- `promptConfig.model`
- `promptConfig.temperature`
- `structuredRules.dsl`
- `enabledIndicators`
- 最新 K 线和上一根 K 线
- `candleProgress`

以下字段不建议进入缓存键：

- `strategyId`
- `strategy.name`
- `createdAt`
- `updatedAt`
- `versionHistory`

### 4.7 验证方式

1. 创建两个策略，使用完全相同的 prompt 和指标。
2. 订阅同一个交易对。
3. 第一轮只应有一次真实 AI API 调用，第二个策略命中缓存。
4. 修改其中一个策略的 prompt 后，应重新调用 AI。
5. 修改模型后，应重新调用 AI。

### 4.8 风险

中等风险。缓存共享必须确保 prompt 和规则完全一致，否则会错误复用其他策略的分析结果。建议先只在完全相同 prompt/rules/model 的策略间共享。

## 6. 修改点三：落地指标组合注册表和 5 分钟预计算

### 6.1 问题

当前 `SymbolBasedScheduler.buildMarketSnapshot()` 只聚合指标类型：

```ts
requiredIndicators: Set<IndicatorType | StatisticsType>
```

但是在 `StrategyEngine.callAI()` 里，仍会按策略参数二次获取：

```ts
getIndicators(symbol, mainTimeframe, 'RSI', { rsiPeriod })
getIndicators(symbol, mainTimeframe, 'MACD', { macdFastPeriod, macdSlowPeriod, macdSignalPeriod })
getIndicators(symbol, mainTimeframe, 'ATR', { atrPeriod })
getIndicators(symbol, oiTimeframe, 'OI', { lookbackMinutes, trendThresholdPercent })
getEMAByPeriods(symbol, mainTimeframe, emaPeriods)
```

当多个策略参数不同或交易对很多时，`analyzeSymbol()` 仍承担大量逐策略指标计算。

### 6.2 新设计

旧方案是“扫描时把参数化指标聚合到快照”。现在修订为更彻底的方案：

```text
策略启停/保存
  -> IndicatorCombinationRegistry 重建实际组合
  -> IndicatorPrecomputeService 每 5 分钟统一计算
  -> StrategyEngine 扫描时按 key 读取已计算结果
```

也就是说，扫描时不再承担指标计算，只负责取结果、预筛、AI 和交易执行。

### 6.3 新增 IndicatorCombinationRegistry

新增文件：

```text
server/modules/indicator-registry/IndicatorCombinationRegistry.ts
```

核心类型：

```ts
interface IndicatorCombination {
  key: string
  symbol: string
  type: IndicatorType | StatisticsType
  timeframe: Timeframe
  params: Record<string, any>
}

interface StrategyIndicatorBinding {
  strategyId: StrategyId
  symbol: string
  keys: Record<string, string>
}
```

核心方法：

```ts
rebuildFromStrategies(strategies: Strategy[]): void
getCombinations(): IndicatorCombination[]
getBinding(strategyId: StrategyId, symbol: string): StrategyIndicatorBinding | undefined
removeStrategy(strategyId: StrategyId): void
```

注册表负责从策略配置中提取：

- `marketData.symbols`
- `marketData.timeframes` 中最小周期作为主周期
- `indicators[].params`
- `statistics[].params`

并生成稳定 key。

### 6.4 新增 IndicatorPrecomputeService

新增文件：

```text
server/modules/indicator-precompute/IndicatorPrecomputeService.ts
```

核心缓存：

```ts
private cache = new Map<string, {
  data: IndicatorData
  computedAt: number
  stale: boolean
}>()
```

核心方法：

```ts

stop(): void
precomputeAll(): Promise<void>
get(key: string): IndicatorData | undefined
getMany(keys: string[]): Map<string, IndicatorData>
markDirtyBySymbolTimeframe(symbol: string, timeframe: Timeframe): void
```

预计算逻辑：

```ts
for (const combo of registry.getCombinations()) {
  if (combo.type === 'EMA') {
    data = await indicatorsHub.getEMAByPeriods(combo.symbol, combo.timeframe, combo.params.periods)
  } else {
    data = await indicatorsHub.getIndicators(combo.symbol, combo.timeframe, combo.type, combo.params)
  }
  cache.set(combo.key, { data, computedAt: Date.now(), stale: false })
}
```

### 6.5 StrategyEditor 当前组合规则

根据 `app/components/StrategyEditor.vue`，短期组合提取规则如下：

- EMA：读取 `params.periods`，如 `[14, 60, 120]`。
- RSI：读取 `params.period`，默认 `14`。
- ADX：读取 `params.period`，默认 `14`。
- MACD：读取 `fastPeriod/slowPeriod/signalPeriod`，默认 `12/26/9`。
- ATR：读取 `params.period`，默认 `14`。
- OI：读取 `changePeriod` 和 `trendThresholdPercent`。
- Volume：读取 `comparePeriod`，默认 `20`。
- SquareHeat：固定 `default`。

注意：只提取“已启用策略实际使用的组合”，不要把 EMA 和 OI 的理论所有组合都算一遍。

### 6.6 修改 StrategyManager

策略生命周期变化时刷新注册表：

## 7. 修改点四：PositionManager 锁键预留 accountId

### 6.1 问题

当前 `PositionManager` 的锁和持仓都是：

`symbol-locks.json` 当前格式：

## 10. 建议实施顺序

### 第一阶段：低风险保护

目标：防止重入和堆积。

改动：

1. `StrategyEngine` 增加全局循环运行锁。
2. 增加 `loopStats`。
3. 扩展 `/api/bot/performance` 输出状态。
4. 保守调整 `bot-config.json`。

预期收益：

- 防止扫描重入。
- 明确看到瓶颈来自 AI、Binance、指标还是批处理。

风险等级：低。

### 第二阶段：AI 缓存共享

目标：减少重复 AI API。

改动：

1. 新增 `server/utils/stable-hash.ts`。
2. 修改 `StrategyEngine.buildAICacheKey()`。
3. 修改 `MultiStrategyAIAnalyzer.buildCacheKey()`。
4. 增加缓存命中日志。

预期收益：

- 相同 prompt/rules/model 的策略复用 AI 结果。
- 策略数量增加时，AI 调用不再完全线性增长。

风险等级：中。

### 第三阶段：指标组合注册表和预计算

目标：减少逐策略重复指标计算。

改动：

1. 新增 `IndicatorCombinationRegistry`。
2. 新增 `IndicatorPrecomputeService`。
3. 策略启停/保存后重建实际指标组合。
4. 每 5 分钟统一预计算所有活跃组合。
5. `StrategyEngine.callAI()` 优先按 key 读取预计算结果。
6. 保留旧的实时计算逻辑作为短期兜底。

预期收益：

- 多策略共享相同参数组合指标，指标计算不再按策略数线性放大。
- `analyzeSymbol()` 变轻。
- 200 个策略如果共用有限指标组合，指标层压力主要取决于交易对数和组合数。

风险等级：中。

### 第四阶段：锁键预留 accountId

目标：为多用户商用做兼容性改造。

改动：

1. `PositionInfo` 增加 `userId/accountId`。
2. `PositionManager` 内部封装 `getPositionKey()`。
3. 兼容旧 `symbol-locks.json`。
4. 写入新持仓时带 `accountId: "default"`。

预期收益：

- 后续多账户不会全项目大面积替换 symbol key。

风险等级：中。

## 11. 回归测试清单

每阶段改完都需要执行以下测试。

### 11.1 策略生命周期

- 创建策略。
- 编辑策略。
- 激活策略。
- 停用策略。
- 删除策略。
- 回滚策略版本。

### 11.2 扫描链路

- 单策略单交易对扫描。
- 多策略同交易对扫描。
- 多策略多交易对扫描。
- 不同扫描间隔策略同时运行。
- 一轮扫描超过 `maxLoopDurationMs` 时是否安全顺延。

### 11.3 指标预计算链路

- 多个策略使用相同 EMA 组合，只生成一个组合 key。
- 多个策略使用不同 EMA 组合，生成多个组合 key。
- 不同 OI 参数生成不同组合 key。
- 每 5 分钟触发一次统一预计算。
- 策略修改后注册表刷新。
- 预计算缺失时能回退实时计算。

### 11.4 AI 链路

- AI 正常返回 LONG/SHORT。
- AI 返回 IDLE。
- AI 超时。
- AI JSON 解析失败。
- 相同 prompt 策略命中缓存。
- 不同 prompt 策略不共享缓存。

### 11.5 Binance 链路

- 获取价格。
- 获取余额。
- 设置杠杆。
- 设置保证金模式。
- 市价开仓。
- 设置止损单。
- 手动平仓。
- 止损触发后本地状态清理。

### 11.6 持仓恢复

- 开仓后重启服务。
- 检查 `active-positions.json` 恢复。
- 检查 `symbol-locks.json` 恢复。
- 平仓后锁释放。

## 12. 不建议短期做的事

短期不建议直接做以下修改：

- 不建议直接把 AI 并发调到很高。
- 不建议绕过 `binanceApiGateway` 直接调用 Binance。

```text
  -> 同 symbol/timeframe/params 组合统一计算一次

AI 缓存按 prompt/rules/model/market 共享
  -> 相同策略逻辑复用结果

仓位锁预留 accountId
  -> 后续多用户可平滑扩展

运行状态可观测
  -> 能明确看到瓶颈并调参
```

这是一条适合当前项目的短期路线：先把重复工作压下来，再做多用户隔离和队列化 Worker。这样不会破坏现有交易逻辑，也能明显降低 AI API 和 Binance API 的压力。
