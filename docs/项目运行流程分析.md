## 三、指标数据获取的"两次分离"机制

### 为什么 EMA 和 OI 要单独获取？

调度器 `buildStrategySubscription()` 中（第119-122行）：

```typescript
requiredIndicators = [
  // 排除 EMA！每个策略的EMA周期参数不同（如 [7,20,50] vs [20,60]）
  ...strategy.indicators.filter(i => i.enabled && i.type !== 'EMA'),
  // 排除 OI！每个策略的OI参数不同（如 changePeriod=6 vs changePeriod=10）
  ...strategy.statistics.filter(s => s.enabled && s.type !== 'OI')
]
```

### 两次获取的流程

```
┌── 第一次：调度器 buildMarketSnapshot() ──────────────────┐
│  批量获取：RSI / MACD / ADX / ATR / Volume                │
│  通过 indicatorsHub.getBatchIndicators()                   │
│  → 合并所有策略需要的指标，一次性请求                       │
│  → 快照可被多个策略复用                                    │
└──────────────────────────────────────────────────────────┘
                         │
                         ▼
┌── 第二次：StrategyEngine.analyzeSymbol() ─────────────────┐
│  单独获取：EMA (通过 getEMAByPeriods)                      │
│  单独获取：OI  (通过 getIndicators('OI'))                  │
│  → 每个策略使用各自的参数配置                              │
│  → 每个交易对每次分析额外发起 2 次调用                      │
└──────────────────────────────────────────────────────────┘
```

### 批量获取不包括 EMA 的验证

`IndicatorsHub.getBatchIndicators()` 中 EMA 会被跳过（第656-661行会输出 warn），必须通过 `getEMAByPeriods` 单独获取。

## 八、重点发现与潜在问题

### 1. EMA 和 OI 的二次获取性能影响
调度器 `buildStrategySubscription` 排除了 EMA 和 OI（第119-122行），导致 `analyzeSymbol` 中需要再次单独调用 `getEMAByPeriods` 和 `getIndicators('OI')`。这意味着**每个交易对每次分析都会额外发起 2 次指标获取调用**。

### 2. 批量获取不包括 EMA 的设计意图
`getBatchIndicators` 中 EMA 会被跳过（第656-661行会输出 warn），必须通过 `getEMAByPeriods` 单独获取——这是有意设计，因为每个策略的 EMA 周期参数不同。

### 3. 所有策略共享同一份 K线缓存
`IndicatorsHub` 的 K线数据是全局共享的（`symbolDataCache`），不同策略即使周期不同，也共享同一份底层数据。

### 4. 事件驱动的增量更新机制
当 K线文件更新时，`subscribeToKLineUpdates`（第846行）会触发 `refreshSymbolTimeframe`，自动重载K线并清除对应指标缓存，下次访问时会重新计算。

### 5. AI 缓存机制
`callAI()` 构建缓存键（基于指标值哈希），相同指标值在 TTL 时间内返回缓存结果，避免重复调用 AI API。

### 6. 全局扫描间隔设计
所有策略运行在同一个全局定时器中，间隔为所有策略 `scanInterval` 的最小值（向上取整到 300秒整数倍）。各策略通过 `nextScanTime` 机制独立判断是否该执行本次扫描。
